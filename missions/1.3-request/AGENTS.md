# Миссия 1.3 · Запрос под результат

Студент собирает полноценный запрос на анализ продаж Q3 — с источниками,
форматом и критерием готовности — и сохраняет его в штаб.

## Цель миссии

Студент умеет собирать запрос из пяти компонентов; в штабе лежит готовый
`briefs/request-q3.md`, который в миссии 1.4 пойдёт в работу.

## Скрипт

### 1. От контекста к запросу

Скажи: «Контекст у нас есть. Но контекст — это фон, а не задание. Между
"разберись с продажами" и рабочим запросом — пять компонентов:

1. **Источники** — какие файлы читать (и только их).
2. **Формат** — как выглядит результат (таблица? выводы? сколько пунктов?).
3. **Ограничения** — чего в результате быть не должно.
4. **Детализация** — глубина: для доклада директору или для себя.
5. **Критерий готовности** — по какому признаку поймём, что результат принят.»

### 2. Разбор на примере «вредного» запроса

Скажи: «Вот типичный запрос аналитика: "Проанализируй продажи за Q3 и скажи,
почему не выполнили план". Пройдись по пяти компонентам: каких здесь нет?»

Check: студент называет: нет источников (модель будет выдумывать), нет формата,
нет критерия готовности, нет ограничений. Достаточно 2–3 верных.

### 3. Собираем запрос по компонентам

Скажи: «Теперь собери запрос для нашего первого реального анализа — файла
`company/data/sales-q3.md`. Называй по одному компоненту, я комментирую.»

Пройди по компонентам по очереди, на каждый — Check и короткая доводка:

1. **Источники** — жди: `company/data/sales-q3.md` + контекст из
   `rok-crisis-room/context.md`. Если предлагает «и логистику, и жалобы» —
   похвали за аппетит, но отложи: «одна миссия — один источник, иначе потом не
   поймём, откуда какой вывод».
2. **Формат** — жди что-то вроде: «3–5 главных наблюдений, каждое с цифрой
   и ссылкой на строку таблицы; в конце — что это может значить, отдельным
   списком гипотез».
3. **Ограничения** — жди: не выдумывать причины, которых нет в файле;
   наблюдения ≠ выводы (помечать раздельно).
4. **Детализация** — жди: уровень доклада директору, но с цифрами,
   которые можно перепроверить.
5. **Критерий готовности** — жди: каждое наблюдение проверяется по файлу,
   гипотезы помечены как гипотезы, ответа «почему» без данных нет.

### 4. Записываем в штаб

Скажи: «Собери это в один запрос и положим в штаб — завтра он пойдёт в работу.»

Action: создай `rok-crisis-room/briefs/request-q3.md` со структурой:

```markdown
# Запрос: анализ продаж Q3

## Контекст
<вставить context.md>

## Источники
- company/data/sales-q3.md (единственный источник цифр)

## Задача и формат
3–5 главных наблюдений о выручке Q3. Каждое наблюдение: формулировка → цифра →
строка таблицы-источника. После наблюдений — отдельный блок "гипотезы"
(что это может значить), помеченный как непроверенное.

## Ограничения
- Никаких причин, которых нет в файле: только наблюдения и помеченные гипотезы.
- Не "сглаживать": если цифра выбивается из общей картины — выделить отдельно.

## Критерий готовности
Каждое наблюдение я могу перепроверить по sales-q3.md за 10 секунд;
гипотезы отделены от наблюдений.
```

Скажи: «Проверь сам: пройдись по пяти компонентам в файле — все на месте?»

Check: студент подтверждает или честно находит дыру (тогда допиши её в файл).

### 5. Завершение

Action: допиши в `rok-crisis-room/diary.md`:

```markdown
## День 3 — запрос под результат

- Собран briefs/request-q3.md по пяти компонентам.
- Правило: одна миссия — один источник, иначе выводы не атрибутировать.
```

Action: перезапиши `.progress/rok.local` строкой `1.3|<текущая дата ISO>`.

Скажи: «Запрос готов. Следующая миссия — боевая: прогоним его по реальным
цифрам Q3. Спойлер: модель ответит уверенно и красиво. И вот тут начнётся
самое интересное. Напиши "готов", когда продолжим.»

## Критерии завершения

- Студент назвал пять компонентов и собрал каждый своими словами.
- Создан `rok-crisis-room/briefs/request-q3.md`, дописан дневник.
- Прогресс записан: `1.3|<дата>`.
